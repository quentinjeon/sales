## 1. 정의

### 1.1 한 문장

**여러 온라인 판매채널의 월별 주문 원장을 표준화·매핑하여, 주문 한 건 단위로 기여이익을 계산하고 제품별·채널별로 집계해 보여주는 손익 관리 도구.**

### 1.2 존재 이유

온라인몰 셀러는 **총매출은 알지만 이익을 모릅니다.** 세 가지가 겹치기 때문입니다.

| 문제 | 결과 |
|---|---|
| 채널마다 수수료율이 다르다 (6.8%~24.0%) | "대충 13%" 가정이 2배 이상 빗나감 |
| 채널마다 상품명 표기가 다르다 | 제품 단위 합산이 안 됨 |
| 원가·물류비가 매출 화면에 없다 | 매출만 보고 "잘 팔린다"고 판단 |

이 시스템은 **"팔수록 손해인 조합"을 숫자로 특정**하는 것을 목적으로 합니다.
매출 리포트가 아니라 **이익 리포트**입니다.

### 1.3 시스템 경계

```
                    ┌─────────────── 시스템 경계 ───────────────┐
                    │                                          │
 채널 어드민 ──엑셀──▶│  적재 → 매핑 → 계산 → 집계 → 출력        │──▶ 대시보드
 (사람이 다운로드)    │                                          │──▶ 결과 엑셀
                    │        SQLite (단일 파일)                 │
                    └──────────────────────────────────────────┘
```

- **입력은 사람이 다운로드한 엑셀**입니다. 채널 API 연동은 범위 밖입니다.
- **단일 사용자·단일 조직**을 가정합니다. 로그인·권한·멀티테넌시가 없습니다.
- **월 단위 배치**로 동작합니다. 실시간 집계가 아닙니다.

### 1.4 만들지 않는 것

| 안 만듦 | 이유 |
|---|---|
| 로그인·권한 | 혼자 쓰는 내부 도구. `127.0.0.1` 바인딩으로 대체 |
| 채널 API 연동 | 채널마다 인증·쿼터가 달라 유지비가 큼. 엑셀로 충분 |
| 재고·발주 | 손익 계산에 재고 흐름이 필요 없음 |
| 부가세 정밀 계산 | 세무는 별도 영역. 모든 금액을 부가세 제외 기준으로 통일 |
| 반품·쿠폰 정밀 처리 | P1 (§10) |

## 2. 핵심 개념 — 딜(Deal)

이 시스템의 모든 계산은 **딜** 단위로 이루어집니다.

> **딜 = 채널 × 제품 구성 × 가격 티어 × 유효기간**

같은 제품이라도 **어느 몰에서 · 어떤 구성으로 · 얼마에** 파느냐에 따라 손익이 다릅니다.
"제품 A의 이익"은 존재하지 않고, **"채널 X에서 구성 Y를 가격 Z에 판 딜의 이익"** 만 존재합니다.

### 2.1 왜 제품 단위로는 안 되는가

| | 한빛홈쇼핑 (수수료 9.5%) | 몰이십일 (수수료 13.0%) |
|---|---:|---:|
| 판매가 | 24,900 | 24,900 |
| − 수수료 | 2,366 | 3,237 |
| − 원가 (760 × 24개입) | 18,240 | 18,240 |
| − 물류비 | 3,000 | 3,000 |
| **= 기여이익** | **1,294 (5.20%)** | **423 (1.70%)** |

같은 제품, 같은 가격인데 **이익이 67% 차이**납니다. 바뀐 것은 채널 수수료율 하나뿐입니다.

### 2.2 딜 구성(DealComponent)

딜은 SKU 여러 개로 구성될 수 있고, 각 구성은 **수량**과 **증정 여부**를 가집니다.

```
딜: "온담 홈캉스 세트" 42,900원
  ├ 즉석밥 24개입  × 12   판매
  ├ 즉석국 15개입  ×  8   판매
  └ 김자반 4개입   ×  2   증정   ← 증정품도 원가에 포함
```

**증정품을 구성에서 빼면 그 원가가 통째로 이익으로 둔갑합니다.**
위 예시에서 김자반을 빼면 원가가 3,700원 줄어 이익이 그만큼 부풀려집니다.

### 2.3 구성수량(pack)이 가장 자주 틀리는 지점

오픈마켓 묶음 상품은 구성수량이 큽니다.

```
원가 = 매입가 × 구성수량
     = 760원 × 24개입   = 18,240원   (즉석밥)
     = 14원  × 1,000개  = 14,000원   (종이컵)
```

구성수량을 빼먹으면 원가가 **수십~수백 배** 작아지고, **전 제품이 흑자로 보입니다.**

## 3. 데이터 모델

### 3.1 테이블 구성

| 구분 | 테이블 | 역할 |
|---|---|---|
| **마스터** | `sku` | 제품 1종 |
| | `sku_cost` | 매입가 **이력** (시점별) |
| | `channel` | 판매채널 |
| | `channel_fee` | 수수료율 **이력** |
| | `channel_logistics` | 물류비 모델 **이력** |
| | `deal` | 판매 단위 (채널×구성×티어×기간) |
| | `deal_component` | 딜의 구성 SKU와 수량 |
| **매핑** | `name_mapping` | 채널 상품명 → 딜 연결 규칙 |
| **원장** | `upload_batch` | 업로드 회차 |
| | `upload_file` | 채널별 파일 (sha256 보관) |
| | `sales_line` | 주문 라인 + **계산 결과 스냅샷** |

> 미사용 테이블 — `file_format` `file_reject` `profit_mart` `reconciliation` `audit_log`.
> PRD 대비 스키마를 먼저 깔아둔 것으로, 현재 코드는 참조하지 않습니다 (§10).

### 3.2 이력 테이블 규칙

`sku_cost` · `channel_fee` · `channel_logistics` 는 **UPDATE 금지**입니다.
값이 바뀌면 기존 행에 `effective_to`를 찍고 **새 행을 추가**합니다.

```
sku_cost:  RICE24  760원  2026-01-01 ~ 2026-07-31
           RICE24  920원  2026-08-01 ~ (현재)
```

조회는 항상 **판매일 기준**입니다.

```
effective_from ≤ 판매일 < effective_to
```

이 규칙이 없으면 8월에 매입가를 올린 순간 **7월 손익이 소급해서 바뀝니다.**

### 3.3 계산 결과는 스냅샷

`sales_line` 은 원본 주문 정보와 **계산 결과를 함께 저장**합니다.

| 원본 | 계산 결과(스냅샷) |
|---|---|
| `order_no` `order_date` `qty` `gross_amount` | `net_revenue` `channel_fee` `cogs` |
| `raw_product_name` `raw_option_name` | `logistics_cost` `contribution_profit` |
| `fee_actual` `is_cancelled` | `margin_rate` `fee_source` `fee_rate_used` |
| `period_month` `period_week` | `confidence` `calc_version` `calculated_at` |

마스터가 나중에 바뀌어도 **과거 손익은 그대로**입니다.
재계산이 필요하면 명시적으로 다시 돌립니다.

### 3.4 무결성 제약

| 제약 | 대상 |
|---|---|
| `fee_rate >= 0 AND fee_rate < 1` | 요율을 %로 잘못 넣는 것 방지 (13 vs 0.13) |
| `unit_cost >= 0`, `price > 0`, `qty > 0` | 음수·0 방지 |
| `tier IN ('NORMAL','EVENT','SPECIAL')` | 티어 오타 방지 |
| `map_status IN ('MAPPED','UNMAPPED','EXCLUDED')` | 상태 오타 방지 |
| `UNIQUE(file_id, order_no, order_line_no, raw_option_name)` | 같은 파일 내 중복 |
| `UNIQUE(channel_id, raw_product_key, raw_option_key)` | 매핑 규칙 중복 |
| `UNIQUE(deal_id, sku_id, is_gift)` | 같은 SKU가 판매/증정로 각 1행 |

## 4. 처리 파이프라인

```
① 적재      엑셀 3장 → 마스터 + 원장
    ↓
② 매핑      채널 상품명 → 딜        (실패 시 UNMAPPED로 남김)
    ↓
③ 계산      주문 라인마다 손익       (실패 시 UNMAPPED로 되돌림)
    ↓
④ 집계      제품별 · 채널별 · 딜별
    ↓
⑤ 출력      대시보드 + 결과 엑셀
```

### 4.1 적재 (`app/services/ingest.py`)

**입력 3종**

| 파일 | 시트 | 들어가는 곳 |
|---|---|---|
| `01_상품정보.xlsx` | `상품정보` | `sku` `sku_cost` `deal`(3티어) `deal_component` |
| `02_채널정보.xlsx` | `채널정보` | `channel` `channel_fee` `channel_logistics` |
| `03_매출_YYYY-MM.xlsx` | **채널명별 시트** | `upload_batch` `upload_file` `sales_line` |

**컬럼 해석** — 채널마다 컬럼명이 다르므로 이름으로 직접 찾지 않고 **키워드 표**로 찾습니다.

| 논리 필드 | 필수 | 후보 키워드 (일부) |
|---|:-:|---|
| 주문일 | ✅ | 주문일자 / 구매확정일 / 결제일 / 정산일 |
| 상품명 | ✅ | 노출상품명 / 주문상품 / 상품명 / 품목명 |
| 수량 | ✅ | 판매수량 / 주문수량 / 개수 |
| 판매금액 | ✅ | 판매금액 / 결제금액 / 상품금액 / 정산금액 |
| 옵션명 | | 등록옵션명 / 선택옵션 / 단품명 |
| 수수료 | | 서비스이용료 / 판매수수료 / 이용료 |
| 취소여부 | | 취소여부 / 주문상태 / 반품 |

채널이 어드민을 개편하면 **키워드만 추가**하면 됩니다.
**필수 컬럼을 못 찾으면 예외**를 냅니다 — 빈 값으로 채우면 매출이 증발합니다.

**중복 방지 3단계**

| 단계 | 검사 | 동작 |
|:-:|---|---|
| ① | 파일 해시(sha256)가 이미 적재됨 | 거부 |
| ② | 이미 적재된 (주문번호, 라인번호, 옵션) | 해당 행 건너뜀 |
| ③ | `replace=True` | 해당 채널×기간을 지우고 재적재 |

①②가 없으면 같은 파일을 두 번 올릴 때 **매출이 정확히 두 배**가 됩니다.

### 4.2 매핑 (`app/services/mapping.py`)

**정규화** — 비교 전에 표기 흔들림을 제거합니다.

```
NFKC 정규화 → 소문자 → [대괄호]·(소괄호) 제거 → 특수문자 제거 → 공백 정리

"[7월 특가] 온담 무균 즉석밥 210g 24개입 햇반 대체"
  → "온담 무균 즉석밥 210g 24개입 햇반 대체"
```

**연결 순서**

| 순서 | 방법 | 결과 |
|:-:|---|---|
| ① | 등록된 규칙(`name_mapping`) 조회 | 즉시 연결 |
| ② | 정규화 후 딜 라벨과 **정확히** 일치 | 연결 + 규칙 자동 등록 |
| ③ | 실패 | **UNMAPPED** — 미매핑 큐로 |

②에서 후보가 여럿이면 옵션명이 티어와 일치하는 것을 고르고,
**그래도 하나로 좁혀지지 않으면 연결하지 않습니다.** 틀리게 붙이느니 미매핑이 낫습니다.

**수동 연결 3가지** (화면 `/mapping`)

| 방법 | 쓰는 때 |
|---|---|
| 자동 후보 수락 | 제안 점수가 높을 때 |
| 제품 DB에서 직접 고르기 | 후보가 틀렸을 때 |
| **여러 제품을 조합해 새 딜 만들기** | 증정품·복합세트 |

**제안 점수** = 0.55 × 이름유사도 + 0.30 × 가격일치 + 0.15 × 구성수량일치

**되돌리기** — `다시 매핑`은 규칙까지 지웁니다. 규칙만 남기면 재계산에서 같은 딜로 다시 붙습니다.

### 4.3 계산 (`app/services/calc.py`)

주문 **한 라인마다** 아래 순서로 계산합니다.

```
① 순매출   = 판매금액                          (취소면 0)

② 수수료   = 파일에 실적값이 있으면 → 그 값        (fee_source=ACTUAL)
             없으면                → round(순매출 × 채널 요율)  (RATE)

③ 원가     = Σ(구성 SKU 수량 × 판매일 기준 매입가) × 판매수량
             증정품 포함. 취소면 0

④ 물류비   = 채널 배송비 모델 × 판매수량
             FLAT → 건당 정액 / CHANNEL_BEARS → 0 / 취소면 0

⑤ 기여이익 = 순매출 − 수수료 − 자사부담할인 − 원가 − 물류비

⑥ 마진율   = 기여이익 ÷ 순매출               (순매출 0이면 null)
```

**취소 건은 매출·수수료·원가·물류비가 전부 0**입니다.
원가만 남기면 취소 1건마다 원가 전액이 이익에서 사라집니다.

**신뢰도(`confidence`)**

| 값 | 조건 |
|---|---|
| `MEASURED` | 수수료가 실적값이거나, 요율 근거가 `MEASURED`/`CONTRACT` |
| `ESTIMATED` | 요율 근거가 `ESTIMATE` 이거나 물류비가 추정치 |

화면의 `추정` 배지는 `ESTIMATED`일 때만 붙습니다.
**실측을 추정처럼 보여도, 추정을 실측처럼 보여도 잘못된 판단을 부릅니다.**

**계산 실패** — 매입가·요율·물류비 모델이 없으면 `CalcError`. 그 라인만 `UNMAPPED`로 되돌리고 사유를 `map_note`에 남깁니다. 배치 전체는 계속 진행합니다.

**역산 함수**

```
손익분기 판매가 = (원가 + 물류비) ÷ (1 − 수수료율)
목표마진 판매가 = (원가 + 물류비) ÷ (1 − 수수료율 − 목표마진율)
목표마진 매입가 = 판매가 × (1 − 수수료율 − 목표마진율) − 물류비
```

### 4.4 집계 (`app/services/report.py`)

`sales_line` 을 직접 집계합니다. 집계 마트를 두지 않습니다 (데이터 규모가 작음).

| 축 | 함수 | 화면 |
|---|---|---|
| 전체 | `totals` | 대시보드 KPI |
| 채널별 | `by_channel` | 대시보드 |
| 제품별 | `by_product` | 대시보드 · 제품 DB |
| 딜별(채널×제품) | `by_deal` | 제품·딜별 수익률 |
| 티어별 | `by_tier` | 대시보드 |
| 주별 | `weekly_trend` | 대시보드 |
| 채널×제품 | `heatmap` | 제품·딜별 수익률 |
| 데이터 품질 | `quality` | 전 화면 |

**집계 대상은 `map_status='MAPPED'` 인 라인뿐**입니다. 미매핑은 별도로 표시합니다.

**기간 키**

```
period_month = 판매일의 달        "2026-07"
period_week  = ISO 주차 (월~일)   "2026-W31"
```

> **월 합계 ≠ 주 합계입니다.** 주차가 월 경계를 걸치기 때문이며 의도된 동작입니다.

### 5.1 대시보드

- KPI 5장 — 총매출 / 기여이익 / 마진율 / 주문건수 / 적자 딜 손실
- **적자 딜 경고** — 마진율 음수인 채널×제품, 항상 최상단
- 채널별 손익 표 (매출 순)
- 제품별 이익 기여 (이익 순)
- **매출 100원의 행방** — 원가·물류·수수료·이익 비중
- 주별 추이 · 가격 티어별 · 데이터 품질
- 월별/주별 토글, 직전 기간 대비 증감

**미완결 기간 회피** — 최신 기간의 건수가 직전 기간의 30% 미만이면 한 칸 물러섭니다. 며칠치만 쌓인 기간을 기본값으로 열면 매출이 급감한 것처럼 보이기 때문입니다.

### 5.2 제품·딜별 수익률

- **채널 × 제품 마진율 히트맵** — 한 행을 가로로 읽으면 채널 간 격차가 보임
- 딜 목록 (마진율 낮은 순)
- **딜 상세** — 판매가부터 기여이익까지 분해 + 채널별 손익분기가 역산 + 대응 옵션

### 5.3 상품명 매핑

- 미매핑 큐 — 자동 후보 3개 + 직접 고르기 + 조합해 새 딜 만들기
- **매핑 완료 목록** — 무엇이 어디에 붙었는지, 방식(자동/직접/조합), 다시 매핑
- **가격 불일치 경고** — 건당 판매가와 딜 가격이 1% 이상 다르면 노란 줄

> 손익은 딜 가격이 아니라 **실제 판매금액**으로 계산하므로 금액이 달라도 매출·이익은 정확합니다.
> 다만 **구성이 다른 딜**에 붙으면 원가가 틀리므로, 가격 차이를 그 신호로 씁니다.

3단계로 분리되어 있습니다.

|---|---|---|

## 9. 설계 원칙

| 원칙 | 이유 |
|---|---|
| **계산 결과는 스냅샷으로 저장** | 마스터가 바뀌어도 과거 손익이 변하면 안 됨 |
| **마스터는 UPDATE 금지, 이력 행 추가** | 위와 같은 이유 |
| **시점 조회는 판매일 기준** | 날짜 없이 집으면 이력이 늘어난 순간 틀림 |
| **증정품도 구성에 포함** | 빼면 원가 누락 → 이익 과대 계상 |
| **구성이 다르면 새 딜** | 기존 딜에 붙이면 원가가 틀림 |
| **미매핑은 조용히 버리지 않는다** | 화면 4곳 + 엑셀 6번 시트에 상시 노출 |
| **금액은 원 단위 정수** | 0.1원이 수천 줄 쌓이면 합계가 안 맞음 |
| **반올림은 수수료에서 한 번만** | 여러 번 반올림하면 합계가 어긋남 |
| **추정과 실측을 구분해 표시** | 둘을 섞으면 잘못된 판단을 부름 |
| **필수 컬럼이 없으면 예외** | 빈 값으로 채우면 매출이 증발 |
| **같은 파일·같은 주문은 두 번 안 넣는다** | 재업로드 한 번에 매출이 두 배 |
| **템플릿 변수는 StrictUndefined** | 이름을 틀리면 빈 화면이 조용히 렌더됨 |

## 13. 용어

| 용어 | 뜻 |
|---|---|
| **SKU** | 재고 단위 제품 1종. 매입가를 가짐 |
| **딜(Deal)** | 판매 단위. 채널 × 구성 × 가격티어 × 기간 |
| **딜 구성(Component)** | 딜에 들어가는 SKU와 수량. 증정품 포함 |
| **구성수량(pack)** | 한 번 팔 때 나가는 개수 |
| **가격 티어** | 정상가 / 일반행사가 / 특가 |
| **순매출** | 판매금액. 취소면 0 |
| **기여이익** | 순매출 − 수수료 − 자사부담할인 − 원가 − 물류비 |
| **마진율** | 기여이익 ÷ 순매출 |
| **미매핑** | 채널 상품명을 딜에 연결하지 못한 상태. 집계에서 제외 |
| **실측 요율** | 정산서에서 역산한 수수료율 (수수료 ÷ 매출) |
| **추정 요율** | 근거를 못 구해 가정한 요율. 화면에 `추정` 배지 |
| **손익분기가** | 이익이 0이 되는 판매가 |
| **`_PLAN`** | 가격표의 13% 가정을 재현하는 가상 채널. 실적 집계 제외 |
